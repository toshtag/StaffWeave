# 正式リリースの判定

正式に配ってよいかを決めるための手順です。

判定は 2 段に分けます。混ぜると、片方だけが済んだ状態を
「リリースできる」と読んでしまいます。

| 段 | 意味 | 誰が確かめるか |
| --- | --- | --- |
| リリース候補 | ソフトウェアとして揃い、機械で確かめられる範囲が通っている | CI |
| 正式リリース | 実機・第三者・試行運用まで済んでいる | 人 |

**リリース候補が整っても、正式リリースにはなりません。**

いま外部の確認へ回している commit と、その間に main へ入れてよいものは、
GitHub の Issue で決めます。外部の確認は数週間かかるため、その間 main が
動き続けると「何を確かめたのか」を言えなくなります。だから候補を止めます。
止めた候補をこの文書へ書き写すと、次の候補ごとに書き換えることになります。

## 1. リリース候補の条件

すべて機械で確かめます。ここに人の判断は入れません。
入れると、確かめた人によって結果が変わり、記録の意味が薄れます。

| 条件 | 確かめ方 | どこで走るか |
| --- | --- | --- |
| lint と書式 | `pnpm lint` | 静的検証 |
| 型 | `pnpm typecheck` | 静的検証 |
| 単体 | `pnpm test:unit` | 静的検証 |
| リポジトリの決めごと | `pnpm check:policy` | 静的検証 |
| 依存の勧告 | `pnpm check:audit` | 静的検証 |
| まっさらな DB への移行 | `pnpm db:migrate` と `pnpm db:verify` | マイグレーションと統合テスト |
| 既存 DB への移行（0025 から最新まで） | `pnpm verify:upgrade` | マイグレーションと統合テスト |
| 書き出しと復元 | `pnpm verify:restore` | マイグレーションと統合テスト |
| 統合 | `pnpm test:integration` | マイグレーションと統合テスト |
| 画面（3 系統） | `pnpm test:e2e` | 画面テスト |
| アクセシビリティ | `e2e/accessibility.spec.ts` | 画面テスト |
| 構造の回帰 | `e2e/cross-browser.spec.ts` | 画面テスト |
| コンテナが組めること | `docker build` | コンテナのビルド |
| 構成一覧 | `pnpm sbom:verify` | SBOM |

手元で通しで確かめるときは `pnpm verify:release-candidate` を使います。
上の表のすべてを、コンテナのビルドと構成一覧の生成まで含めて通します。

`pnpm verify` は毎日の作業向けで、コンテナのビルドと構成一覧を含みません。
配れる状態かの判定には使えません。

どちらも `psql` と `pg_dump`（PostgreSQL クライアント）が要ります。

## 2. 成果物と、元にしたソースの対応

配るものと、それが何から出来ているかを結び付けます。
結び付いていないと、受け取った側は中身を自分で確かめられません。

| 出すもの | どうやって出すか | 元をどう辿るか |
| --- | --- | --- |
| コンテナ画像 | `docker build -f docker/api.Dockerfile` | 画像の digest |
| 構成一覧（workspace） | `pnpm sbom:generate` | `metadata.component.properties` の `staffweave:source-sha` |
| 構成一覧（コンテナ） | 同上 | 同上と、`metadata.component.version` の画像 digest |
| チェックサム | 同上（`.sha256`） | 並べて配る |
| 打刻端末の配布物 | `./scripts/package-agent.sh` | 作った commit を記録欄へ書く |

対応は `pnpm release:manifest` でまとめて出せます。

**条件が揃わなければ、一覧を出さずに非 0 で終わります。**
作業中の変更、branch の上に居ないこと、Docker が無いこと、構成一覧の欠落、
チェックサムの不一致、書いてある commit の不一致が対象です。

文章で「配れません」と書きながら 0 で終えると、判定へ組み込んだときに
条件を満たさない commit がそのまま通ります。

## 3. 署名とタグ

**どちらも所有者が行います。この判定の手順には含めません。**

署名には所有者の鍵が要ります。鍵を持たない者が手順だけ整えても、
署名の意味（誰が配ったか）が失われます。

タグの候補は、リリース候補の条件をすべて満たした commit です。
`pnpm release:manifest` が候補を出します。付けるかどうかは所有者が決めます。

## 4. 正式リリースの前に、人が確かめること

以下は機械では確かめられません。**未実施のまま正式リリースへ進まないでください。**

記録は、この文書ではなく別の記録として残してください。
ここへ書き足すと、次に確かめ直したときに古い記録が残ります。

### 4.1 実機の打刻端末

手順とチェックリストは
[operations/device-agent-service.md](../operations/device-agent-service.md) にあります。

| 項目 | 期待する結果 | 実施日 | 実施者 | 結果 |
| --- | --- | --- | --- | --- |
| 物理の IC カードで登録・打刻 | 登録したカードで打刻でき、未登録・失効のカードでは打刻されない | | | |
| Windows で起動時の常駐として登録 | 登録でき、端末の再起動で自動で上がる | | | |
| 送信待ちを残した状態での再起動 | 上がったあとに送られ、記録が失われない | | | |
| 回線を抜いた状態からの復帰 | つなぎ直すと送られ、間隔が広がっている | | | |
| 端末の時計を大きくずらす | サーバー側で時計差として記録される | | | |

### 4.2 第三者によるセキュリティ確認

自分で書いたものを自分で見ても、前提そのものの誤りには気付けません。

| 項目 | 期待する結果 | 実施日 | 実施者 | 結果 |
| --- | --- | --- | --- | --- |
| 認証・セッションの確認 | 重大・高リスクの指摘が無い | | | |
| 認可（誰が何を見られるか）の確認 | 同上 | | | |
| 秘密情報の扱いの確認 | 同上 | | | |
| 外部へ出る経路（Webhook・CSV）の確認 | 同上 | | | |
| 指摘への対応 | 重大・高リスクが残っていない | | | |

### 4.3 試行運用

検査で通ることと、実際の職場で使えることは別です。

**条件を「1 カレンダー月の実運用」から次へ変えました。**
厳密に維持すると、最短でも 1 か月待つことになります。待っている間に main は動き続け、
何を確かめたのかが言えなくなります。

- 1 か月相当の代表データを使った、月末ライフサイクルの演習
- 5 営業日の実機・実利用者によるパイロット
- 打刻 → 訂正 → 申請 → 段階承認 → 休暇 → 締め → 解除 → 再締め → 給与 CSV まで通す

この条件を満たしたことは書けますが、**「1 か月実運用済み」とは書きません。**
確かめたのは 1 か月ぶんのデータであって、1 か月の実運用ではありません。

| 項目 | 期待する結果 | 実施日 | 実施者 | 結果 |
| --- | --- | --- | --- | --- |
| 1 か月相当の代表データによる月末ライフサイクル演習 | 打刻・訂正・申請・段階承認・休暇・締め・解除・再締め・給与 CSV を最後まで通せる | | | |
| 5 営業日の実機・実利用者パイロット | 実際の利用者が、日々の打刻と申請を止まらずに行える | | | |
| 給与への引き渡し | 出力した値が、給与側で受け取れる | | | |
| 締めのやり直し | 解除して締め直したとき、渡した値との違いを説明できる | | | |
| 問い合わせの記録 | 使い方が分からず止まった場面が残っている | | | |

### 4.4 まだ作っていない機能の確認

まだ無いものは [guide/features.md](../guide/features.md) に並べています。
招待・パスワード再設定の自己申請、MFA・SSO、メトリクスとアラート、
保持期間を過ぎたデータの自動削除、端末の自動更新は、運用の手順で回します。

導入する組織の事情がその回し方と合わない場合は、正式リリースではなく、
その項目を先に作ってください。

## 5. リリース候補を妨げるもの

まだ無いもののうち、リリース候補の条件を妨げるものはありません。
業務を回すために要るものは実装済みで、残りには運用での回し方があります。

**ただし正式リリースは、4 章の外部の確認が済むまで行えません。**
実機の打刻端末（IC カードと Windows での常駐）、第三者によるセキュリティ確認、
試行運用です。実施者が証拠を記録する場所として、それぞれ Issue を立ててあります。

## 6. 正式版を配る

4 章がすべて済み、重大・高リスクの Issue が 0 になったら配れます。

版は `package.json` の `version` が正本です。ここを直してから tag を付けます。
2 か所で決めると、必ずどちらかが古くなります。

```sh
pnpm verify:release-candidate     # 機械で確かめられる範囲
pnpm release:assets               # 配るものを組む
pnpm release:verify               # 配るものと元の対応を確かめる
```

`pnpm release:assets` が出すもの:

| 成果物 | 中身 |
| --- | --- |
| `staffweave-agent-<版>.zip` | 打刻端末の配布物。展開してそのまま置ける |
| `staffweave-workspace.cdx.json` | リポジトリの構成一覧 |
| `staffweave-container.cdx.json` | コンテナの構成一覧 |
| `SHA256SUMS.txt` | 上のすべての checksum |
| `release-manifest.txt` | 版・commit・成果物の対応 |

`v<版>` の tag を押すと、`.github/workflows/release.yml` が同じものを組み直し、
元との対応を確かめてから GitHub Release を作ります。
tag を作らずに確かめたいときは、同じワークフローを手動で実行してください。

**署名はしません。** 署名には所有者の鍵が要り、鍵を持たない者が付けた署名は
「誰が配ったか」を示せません。受け取った側は `SHA256SUMS.txt` と、
構成一覧に書かれた commit で中身を確かめます。

コンテナは registry へ配りません。配るのはセルフホスト用の一式で、
受け取った側が `docker/api.Dockerfile` から組みます。組んだ結果の構成は
`staffweave-container.cdx.json` に載っています。

## 7. 判定の記録

判定した結果は、次の 3 つを揃えて残します。

- 対象の commit（40 桁）
- リリース候補の条件を満たした CI の実行 URL
- 4 章の表を埋めたもの

3 つが揃っていない判定は、判定として扱いません。
