「何を確かめたのか」が誰にも言えなくなります。だから候補を止めます。

### この候補で足したもの

前の候補（`f9b5795`）との差は #284 と #285 です。

**起動したときに装置が無いと、常駐そのものが終わっていました。** 受け渡しを作る
時点で最初の装置を待っており、30 秒見えなければそこで失敗します。開き直しの輪へ
入る前なので、上げ直しの回数を使い切ると止まったままになります。装置の認識が遅い、
あとから挿す、USB の口の初期化が遅れる、はどれも普通に起こることです。

運用の文書には「止まりはしません」と書いてありました。書いたほうが正しいので、
実装を合わせています。装置を待つのは `waitForCard` の側で、30 秒は 1 回の待ちを
区切るだけです。

**SYSTEM で動かす相手の権限を見ていませんでした。** 確かめていたのは資格情報の
置き場だけで、起動する Node と配布物は見ていません。標準の利用者が書き換えられる
場所へ展開しても登録でき、次に上がったときそのコードが SYSTEM で動きます。
配布物・起動する JS・Node とその置き場を確かめ、絞った場所へ置く手順も足しました。

## 2. 前の候補との違い

最初の候補（`6edb299`）は、v0.1 の必須機能を満たしていましたが、
`docs/product/capability-matrix.md` に `partial` 14 件・`planned` 18 件が残っていました。
（いまの一覧は `implemented` 105 件・`partial` 17 件・`planned` 9 件・`non-goal` 5 件です。
`partial` が増えたのは能力が減ったからではなく、縦に通る証拠の無いものを
`implemented` と書くのをやめたためです。）
「候補になった」ことと「当初想定した製品像が完成した」ことは同じではありません。

取り下げた候補では、その差を埋めたつもりでいました（[roadmap.md](../roadmap.md) の P27）。
実際には、次のうちいくつかは API としては存在しても、利用者が使う経路から
計算や保存まで届いていませんでした。

- 承認しきった残業・休日出勤・打刻修正を、日次の計算へ効かせる
- 週・清算期間・変形労働の対象期間の集計
- 休暇の付与規則と、自動付与・一斉付与・CSV 取込・管理簿・失効予定
- 申請まわりの通知（正本は DB）
- 勤務区分と申請種別の CSV 一括投入
- 長時間労働の警告
- IC カードの読み取り（PC/SC）と、打刻時の位置情報（組織ごとの opt-in）
- 正式版を配る仕組み（版の正本・成果物・checksum・対応の検証・release workflow）

残っている `partial` と `planned` は
[capability-matrix.md](../product/capability-matrix.md) が正本です。
いずれも、実機で確かめていないものか、v0.1 の範囲外として次期へ回したものです。

## 3. 凍結の範囲

候補を止めている間、main へ入れてよいのは次だけです。

- 外部の確認で見つかった、重大・高リスクの修正
- リリースを妨げる不具合の修正
- 文書の誤りの訂正

**新しい機能は入れません。**

入れたくなったら、それは v0.1 に要るものだったということです。
[product/v0.1-scope.md](../product/v0.1-scope.md) の判断が間違っていたことになるので、
機能を足す前に、その文書を直してください。

## 5. 候補が変わるとき

重大・高リスクの修正を入れると、候補の commit は別のものになります。

そのとき、古い候補で得た確認の結果を、そのまま新しい候補の結果として使えません。
何を直したかによって、やり直す範囲が変わります。

| 直したもの | やり直すもの |
| --- | --- |
| 端末・Agent・登録 | 実機の確認 |
| 認証・認可・秘密情報・外部へ出る経路 | 第三者の確認 |
| 打刻・申請・承認・締め・給与への引き渡し | 試行運用のうち、その経路 |
| 上記に触れない文書だけ | なし |

やり直す範囲を決めたら、この文書の 1 章と 4 章を新しい候補で書き直します。

## 6. 正式リリースの判断

4 つの確認がすべて済み、重大・高リスクの Issue が 0 になったら、
最後の候補で次を実行します。

```sh
pnpm verify:release-candidate
pnpm release:assets
pnpm release:verify
```

そのうえで `v0.1.0` の tag を押すと、`.github/workflows/release.yml` が
その commit を確かめてから、同じものを組み直し、元との対応を確かめて
GitHub Release を作ります。

確かめるのは 2 つです。tag の名前と package の版が一致していること、
そして **その SHA で** 必須の workflow（CI・実行時の検証・SBOM・Windows の配布物）が
成功していること。
どちらかを満たさなければ、成果物を組むところまで進みません。

branch の最新が緑であることは、tag を押した commit が緑であることを
意味しません。古い成功は流用できません。

「実行時の検証」は対象を絞っているため、文書だけを直した commit では走りません。
候補として凍結したい commit がそれに当たる場合は、Actions からその ref を指定して
手で走らせ、その SHA の成功を作ってください。走らせずに通す道はありません。

揃えるものは [checklist.md](checklist.md) の 6 章にあります。

署名は行いません。署名には所有者の鍵が要り、鍵を持たない者が付けた署名は
「誰が配ったか」を示せません。
