# Webhook 送信先のネットワーク方針

Webhook の送信先は利用者が登録します。何の制限も置かなければ、staffweave 自身が
内部ネットワークへ HTTP 要求を出す道具になります。ここでは何をどこまで守るのかを固定します。

実装は `packages/api/src/integration/webhook-network-policy.ts` と
`packages/api/src/integration/webhook-http-transport.ts` にあります。

## 設定

| 値 | 意味 |
| --- | --- |
| `public-only`（既定） | 公開ネットワークとして扱えるアドレスだけを許す |
| `allow-local` | ループバック・RFC 1918 の私設ネットワーク・IPv6 ユニークローカルを追加で許す |

判定は次の 3 分類へ分けています。順序に意味があり、常時拒否をローカル許可より先に見ます。
こうしないと、`allow-local` が常時拒否の宛先を上書きできてしまいます。

| 分類 | 扱い |
| --- | --- |
| 常時拒否 | どちらの設定でも拒否する |
| ローカル | `allow-local` のときだけ許す |
| 公開 | どちらの設定でも許す |

IPv6 の「公開」は、拒否一覧に無いことではなく、グローバルユニキャストとして
割り当てられた範囲（`2000::/3`）に入っていることを条件にします。
特別用途の範囲は後から増えるため、拒否一覧だけを頼りにすると、
新しい範囲が追加されるたびに穴ができます。

範囲は IANA の Special-Purpose Address Registry と
IPv6 Global Unicast Address Assignments を基準にしています（確認日: 2026-07-31）。
実行時に取得はせず、割り当てが変わった場合は別 Issue で一覧とテストを更新します。

`WEBHOOK_NETWORK_POLICY` は API とワーカーの両方が読みます。
片方だけを緩めた状態を作らないよう、不正な値ではどちらのプロセスも起動しません。

`allow-local` は明示的な運用上の例外です。
外部の利用者が送信先を登録できる運用では `public-only` のままにしてください。
自分だけが送信先を登録し、送り先が自分の管理下の内部サービスである場合にだけ選びます。

`allow-local` でも次は常に拒否します。

- リンクローカル（`169.254.0.0/16`, `fe80::/10`）
- クラウドのメタデータサービス（`169.254.169.254`, `fd00:ec2::254`, `fd20:ce::254`）
- 公開空間にありながら基盤の内部通信へ割り当てられている仮想アドレス（`168.63.129.16`）
- 未指定・マルチキャスト・ブロードキャスト・予約済み・文書用・ベンチマーク用
- Carrier-grade NAT、IPv4 射影・変換用の IPv6 範囲

IPv6 ユニークローカル（`fc00::/7`）は `allow-local` で内部サービス宛として使えますが、
その中にあるメタデータエンドポイントだけは拒否します。
`fc00::/7` 全体を常時拒否にはしません。それでは内部サービスへ送れなくなります。

## 検査の内容

1. URL の構文。`http:` と `https:` 以外、URL 内の認証情報、フラグメント、ポート 0 を拒みます。
   判定は WHATWG の `URL` で正規化してから行います。文字列の見た目では
   `http://2130706433/` のような別表記のループバックを見落とします。
   長さは入力と正規化後の両方を 2048 文字で見ます。上限は
   `packages/domain/src/integration/webhook.ts` の定数を API 契約と共有します。
2. 名前解決。返ったアドレスをすべて検査し、一つでも許可されないものがあればホストごと拒みます。
   安全なアドレスだけを選んで送ると、応答順や実装差で内部側が選ばれる余地が残ります。
   解決には中断できる DNS 問い合わせを使い、登録時は
   `WEBHOOK_TARGET_VALIDATION_TIMEOUT_MS`（既定 3000 ミリ秒）、送信時は
   `WEBHOOK_SEND_TIMEOUT_MS` で打ち切ります。送信の上限時間には、
   名前解決から応答の読み取りまでを含めます。
   `dns.lookup()` は打ち切れず、遅い解決が溜まると同じプロセスの他の処理まで巻き込むため使いません。
   代償として `hosts` ファイルだけにある別名は解決できません。
   ローカルの送信先は、DNS で引ける名前（コンテナのサービス名など）か
   IP リテラルで指定してもらう必要があります。
3. 接続先の固定。検査した候補を HTTP クライアントへ直接渡し、接続の直前に
   名前を引き直させません。候補は 1 件へ絞らず、全件が検査済みであることを根拠に
   Node.js の種別自動選択へ渡します。到達できない種別だけが残って送れなくなる状態を避けます。
   HTTPS では、接続先を固定したうえで元のホスト名に対して証明書を検証します。
   接続を通すために検証を緩めることはしません。
4. リダイレクト非追従。3xx は通常の応答として受け取り、失敗として記録します。
   Agent と connector も同じ理由で追従しません（`packages/agent/src/client.ts`、
   `packages/connector/src/index.ts`）。外向きに秘密情報を送る経路では、
   検査できるのは最初の宛先だけで、転送先は確かめられないためです。
5. 応答の上限。ヘッダー 16 KiB、本文 64 KiB。本文は保存もログ出力もしません。

## 暗号化

公開ネットワークとして扱う送信先には `https` を必須にします。

| 送信先 | `http` | `https` |
| --- | --- | --- |
| 公開ネットワーク | 拒否 | 許可 |
| ローカル（`allow-local` のとき） | 許可 | 許可 |

Webhook の本文には勤怠・申請の内容が入ります。署名は改変を見つけるためのもので、
本文と署名の秘匿性は与えません。平文で送れば、内容も署名値もそのまま観測できます。

`public-only` では、そもそもローカル宛を許さないため、`http` の送信先は登録も送信もできません。
`allow-local` でも、`http` を許すのは名前解決の結果がすべてローカルの範囲に収まる相手だけです。
公開アドレスへ解決される相手は、設定に関わらず `https` を求めます。

判定は名前解決の後に行います。ホスト名の見た目では、その相手がローカルかどうか分かりません。

検査は登録時と送信の直前の両方で行います。登録時だけでは、登録後に名前解決の結果が
内部アドレスへ変わる場合、設定を `allow-local` から `public-only` へ戻した場合、
データベースへ直接書かれた行がある場合を防げません。

検査で拒否した送信は、送信履歴へ `failed` として残します。自動再送はしません。
再送すれば同じ理由で拒否されるだけで、拒否の記録だけが増えます。

## この方針で守れないこと

送信先が公開ネットワークにあることは、その相手を信頼してよい理由にはなりません。
受け取り側では引き続き次が必要です。

- 受信経路の認証
- `x-staffweave-signature` の検証
- `eventId` による重複排除

送信先ごとの許可アドレス一覧、ワークスペースごとのネットワーク方針、
プロキシ経由の送信は扱いません。これらが必要になった時点で別の Issue として設計します。
