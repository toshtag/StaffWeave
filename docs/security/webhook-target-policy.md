# Webhook 送信先のネットワーク方針

Webhook の送信先は利用者が登録します。何の制限も置かなければ、staffweave 自身が
内部ネットワークへ HTTP 要求を出す道具になります。ここでは何をどこまで守るのかを固定します。

実装は `packages/api/src/integration/webhook-network-policy.ts` と
`packages/api/src/integration/webhook-http-transport.ts` にあります。

## 設定

| 値 | 意味 |
| --- | --- |
| `public-only`（既定） | 公開ネットワークとして扱えるアドレスだけを許す |
| `allow-local` | ループバック・RFC 1918 の私設ネットワーク・IPv6 ユニークローカルを追加で許す |

`WEBHOOK_NETWORK_POLICY` は API とワーカーの両方が読みます。
片方だけを緩めた状態を作らないよう、不正な値ではどちらのプロセスも起動しません。

`allow-local` は明示的な運用上の例外です。
外部の利用者が送信先を登録できる運用では `public-only` のままにしてください。
自分だけが送信先を登録し、送り先が自分の管理下の内部サービスである場合にだけ選びます。

`allow-local` でも次は常に拒否します。

- リンクローカル（`169.254.0.0/16`, `fe80::/10`）
- クラウドのメタデータサービス（`169.254.169.254` など）
- 未指定・マルチキャスト・ブロードキャスト・予約済み・文書用・ベンチマーク用
- Carrier-grade NAT、IPv4 射影・変換用の IPv6 範囲

## 検査の内容

1. URL の構文。`http:` と `https:` 以外、URL 内の認証情報、フラグメント、ポート 0 を拒みます。
   判定は WHATWG の `URL` で正規化してから行います。文字列の見た目では
   `http://2130706433/` のような別表記のループバックを見落とします。
2. 名前解決。返ったアドレスをすべて検査し、一つでも許可されないものがあればホストごと拒みます。
   安全なアドレスだけを選んで送ると、応答順や実装差で内部側が選ばれる余地が残ります。
3. 接続先の固定。検査したアドレスを HTTP クライアントへ直接渡し、接続の直前に
   名前を引き直させません。HTTPS では、接続先を固定したうえで元のホスト名に対して
   証明書を検証します。接続を通すために検証を緩めることはしません。
4. リダイレクト非追従。3xx は通常の応答として受け取り、失敗として記録します。
5. 応答の上限。ヘッダー 16 KiB、本文 64 KiB。本文は保存もログ出力もしません。

検査は登録時と送信の直前の両方で行います。登録時だけでは、登録後に名前解決の結果が
内部アドレスへ変わる場合、設定を `allow-local` から `public-only` へ戻した場合、
データベースへ直接書かれた行がある場合を防げません。

## この方針で守れないこと

送信先が公開ネットワークにあることは、その相手を信頼してよい理由にはなりません。
受け取り側では引き続き次が必要です。

- 受信経路の認証
- `x-staffweave-signature` の検証
- `eventId` による重複排除

送信先ごとの許可アドレス一覧、ワークスペースごとのネットワーク方針、
プロキシ経由の送信は扱いません。これらが必要になった時点で別の Issue として設計します。
