# Webhook の署名鍵

Webhook の署名は対称鍵の HMAC です。送信側は署名を作れる鍵を持たざるを得ません。
データベースに保存している値は、照合しかできないハッシュではなく、
**そのまま正当な署名を作れる鍵**です。ここではその事実と、運用上の責任を固定します。

実装は `packages/api/src/integration/webhook-signature.ts` と
`packages/connector/src/index.ts` にあります。

## 署名方式

| 項目 | 値 |
| --- | --- |
| 署名方式 | HMAC-SHA256（`WEBHOOK_SIGNATURE_SCHEME` = `hmac-sha256-v1`） |
| 鍵の導出 | SHA-256 の小文字 16 進数（`WEBHOOK_SIGNING_KEY_DERIVATION` = `sha256-hex-v1`） |
| 署名対象 | `canonicalWebhookMessage()` が組み立てる文字列 |
| 署名の形式 | Base64 |

署名対象は次の 5 行を改行で連結したものです。

```text
staffweave-webhook/1
<eventId>
<eventType>
<timestamp>
<body>
```

`timestamp` は送信を試みた時刻、`body` は送信した本文そのものです。
ヘッダーは `x-staffweave-event`, `x-staffweave-event-id`,
`x-staffweave-timestamp`, `x-staffweave-signature` の 4 つです。

## 登録時の秘密

送信先を登録すると、応答の `secret` に署名用の秘密が一度だけ返ります。

- 一覧では返りません。再表示もできません。
- 受け取り側が安全に保存し、`verifyWebhook()` へ渡します。
- 失った場合は送信先を登録し直します。ローテーション用の API はまだありません。

## 鍵の導出

`secret` はそのまま HMAC の鍵にはしません。次の手順で 64 文字の鍵を導きます。

1. `secret` を UTF-8 のバイト列として SHA-256 にかける
2. 小文字 16 進数 64 文字にする
3. **その 64 文字を UTF-8 の文字列のまま** HMAC の鍵として使う

ダイジェストの生の 32 バイトは使いません。表現を変えると、
すでに登録済みの送信先の署名がすべて変わります。

受け取り側は手計算せず、`@staffweave/connector` を使ってください。

```ts
import { deriveWebhookSigningKey, verifyWebhook } from '@staffweave/connector';

// 通常はこれだけでよい。導出は内部で行う。
const event = verifyWebhook(secret, { headers, body });

// 自前で署名を組み立てる場合の鍵。値は署名を作れる機密情報。
const signingKey = deriveWebhookSigningKey(secret);
```

## データベースの保存値

保存先は `webhook_endpoints.signing_key` です。

- 導出後の 64 文字（`deriveWebhookSigningKey(secret)` と同じ値）を保存します。
- **照合用のハッシュではありません。** この値を読めた者は、任意の本文に対して
  正当な署名を付けられます。受け取り側は本物との区別ができません。
- 「一方向ハッシュで保護されている」という説明は誤りです。そう説明しません。
- 対称鍵である以上、署名能力を保ったまま保存値を一方向ハッシュだけにはできません。

通常の送信先一覧や送信待ちの登録では署名鍵を取得せず、
送信ワーカーが通知を処理する直前にだけ取得します。

0013 のマイグレーションでは `secret_hash` という名前で、
「以後はハッシュで照合する」と説明していました。0015 で `signing_key` へ改めています。
0013 は適用済みでチェックサムの対象のため書き換えられません。履歴上の記録として残ります。

## 機密区分

`signing_key` は**機密情報**です。次のすべてに含まれます。

| 場所 | 含まれるか |
| --- | --- |
| データベース本体 | 含まれる |
| リードレプリカ | 含まれる |
| `pg_dump` の出力 | 含まれる |
| ボリュームのスナップショット | 含まれる |
| `pnpm backup` の出力 | 含まれる |
| API の応答 | 含まれない |
| 送信先の一覧 | 含まれない |
| ログ | 含まれない |

## 運用上の注意

- データベースの読み取り権限を必要最小限にします。
  参照専用の利用者にも `webhook_endpoints` を見せない構成を検討してください。
- バックアップとスナップショットを暗号化し、閲覧できる者を限ります。
- 署名鍵をログ・監視・障害報告へ貼らないでください。
- 漏えいが疑われる場合は送信先を登録し直し、受け取り側の秘密を差し替えます。
  現時点で専用のローテーション API はありません。

## 現在の限界

- アプリケーションレベルでの署名鍵の暗号化は実装していません。
  保存値は平文です。守るのはデータベースとバックアップの管理です。
- 外部の秘密管理サービスや鍵管理サーバーは使いません。
- 非対称署名（受け取り側が検証鍵だけを持つ方式）は対象外です。
  採用する場合は署名方式の切り替えと既存送信先の移行を別途設計します。
- 署名鍵のローテーション API、送信先の更新 API はありません。
