# 開発方針

StaffWeave の実装判断で迷ったとき、この文書が優先されます。

## 設計の前提

以下は個別の判断より上位にあり、下の各節はこの前提を具体化したものです。

- **セルフホスト優先。** 単一の PostgreSQL と Docker Compose で起動できることを最優先にする。
  同一コードベースで将来 SaaS 運用できるよう、Workspace 分離は最初から持つ。
- **モジュラーモノリス。** マイクロサービス、Kubernetes、Redis、Kafka は導入しない。
- **観測イベントは不変。** 打刻の取り消しや修正は、元イベントを書き換えず追加記録で表現する。
- **自動確定しない。** PC ログや IC カードの記録だけで勤務時間を確定させない。
  これらは証拠・候補・乖離検出として扱う。

## 技術選定

| 領域 | 採用 |
| --- | --- |
| 言語 | TypeScript（strict） |
| 実行環境 | Node.js LTS |
| パッケージ管理 | pnpm workspace |
| データベース | PostgreSQL |
| HTTP | Hono |
| フロントエンド | React + Vite |
| テスト | Vitest（unit / integration）、Playwright（E2E） |
| 実行構成 | Docker Compose |
| 同期状態遷移 | fsmxjs |
| 画面の言語 | `ja-JP` と `en` |

導入しないもの: マイクロサービス、Kubernetes、Redis、Kafka、ORM による暗黙のクエリ生成。

## アーキテクチャ制約

- モジュラーモノリスから開始する。
- ドメイン、勤怠計算、状態遷移、API 契約をフレームワークから分離する。
- React 型、Hono 型、DB 型、外部 SDK 型をドメイン層へ持ち込まない。
  ドメイン層が依存してよいのは TypeScript 標準ライブラリと fsmxjs のみ。
- DB アクセスは明示的な SQL と Repository 境界を基本とする。
- OpenAPI 3.1 と JSON Schema を Web・Agent・外部連携の共通契約にする。
- 外から来る値（本文・経路の識別子・クエリ文字列）は、契約で検証してから先へ渡す。
  検証は経路ごとに書かず、共通の入口（`packages/api/src/shared/request.ts`）を通す。
  経路ごとに書くと、書いた経路だけが契約どおりになる。
- 経路が受け取る引数は、契約に宣言したものと一致させる。
  契約にあって読まない引数、読んでいて契約に無い引数を残さない。
- fsmxjs は申請・承認・締め・端末登録などの同期状態遷移に限定して使う。
  非同期処理やデータ取得の制御には使わない。

## データの扱い

- 元の打刻・観測イベントは上書きしない。修正・承認・計算版を追跡可能にする。
- PC ログや IC カード情報だけで勤務時間を自動確定しない。証拠・候補・乖離検出として扱う。
- 生のカード識別子など、再利用されると危険な値はそのまま保存しない。
- 秘密情報、実在人物、実在企業のデータをコミットしない。

## テナント境界

- すべての業務データは `workspace_id` を持つ。
- Repository は `workspace_id` を必須引数として受け取り、SQL の `WHERE` 句に必ず含める。
- 他 Workspace のデータを参照できないことをテストで検証する。

## 表現の制約

- 完全な不正防止や法令適合を保証する表現をしない。
- 未実装機能を文書や UI で提供済みと表現しない。
  いま動くものの一覧は [features.md](../guide/features.md) に書く。
- 実装済みの機能を未実装と表現しない。過小に書くのも、過大に書くのと同じ誤りとして扱う。
- 画面に「まだ実装されていません」と告げる文言を置かない。
  画面は消し忘れても誰も落ちないため、実装が進むたびに古い告知だけが残る。
- 他の製品を引き合いに出して説明しない。機能の要件は StaffWeave の設計として書く。
  引き合いに出すと、相手の名前や画面の写しが入り込む入口になり、
  相手の版が変われば説明だけが古くなる。
- 止めたい固有名そのものをリポジトリへ書かない。符号化しても元へ戻せるため同じ。
  検査が要るなら、値を外から渡す。`POLICY_FORBIDDEN_PATTERN` を repository variable
  として置くと、`pnpm check:policy` が中身・ファイル名・branch・commit・PR の
  すべてへ同じ規則を当てる。
  CI では、渡されていないこと自体を失敗にする。渡し忘れて通ると、検査が外れた
  ことに気付く機会が無いまま外れたままになる。設定の欠落は誰も見ない。
  手元では止めない。この語はワークスペース側の設定で、複製しただけの人が
  持っていないのはふつうの状態。
- 決めていない設定を、実行時に既定値で埋めない。埋める値をどれだけ狭くしても、
  決めていない設定で処理が進む点は変わらない。断るなら、入口の側で断る。
  出口で断ると、すでに進んでいるものが途中で止まり、始めた人には理由が見えない。
- 語を止める規則は、中身だけでなく Git の全ての経路へ当てる。
  中身だけを見る検査は、中身だけを直せば通る。branch 名・commit・PR の本文へ
  同じ語を書いても止まらない。入口を 1 つ塞いでも、他の入口から同じものが入る。
  ログへ出すのは経路ごとの件数だけにする。一致した行を出すと、伏せたい語が
  そのまま PR の画面へ残る。
- 画像と PDF を Git で追跡しない。出所は問わない。
  差分で中身を読めないため、何が写っているかを確かめないまま再配布することになる。
  外から持ち込んだ資料が混ざっても、レビューでは気付けない。
  図は本文か SVG で書く。視覚回帰を入れるときは、同じ CI の中で base の版と候補の版を
  描画して比べ、生成した画像は成果物として残す。
  第一者が作った画像を置く必要が出たら、この決めごとを先に見直す。
  置き場と出所の記録を決めてから、検査を許可制へ変える。

## 実装の進め方

- 受け入れ条件を先に短く定義してから実装する。
- 文書を先に大量作成せず、実装に必要な最小限を同じ変更で更新する。
- 使われない抽象化、空パッケージ、将来用だけのコードを作らない。
- 一時的な TODO を残す場合は、理由と解消条件を明記する。
- 範囲外の問題は勝手に拡張せず、重大でなければ Issue へ記録して次へ進む。
- 課題と完了条件は GitHub Issue、実装差分と検証結果は PR、機械的な合否は CI を正本とする。
  同じ状態を写した進捗ファイル・計画ファイル・タスクファイルをリポジトリへ増やさない。
  同じ完了状態を複数の場所へ置くと、必ずどこかが古くなる。
- いま何が動くかは [features.md](../guide/features.md) にだけ書く。
  個々の課題の進み具合はここへ写さない。
- 文書のためだけの独自の解析器を作らない。Markdown の形を厳密に読む検査は、
  確かめられるのが「表が壊れていないか」までで、書いてあることが本当かは分からない。
  文書を直すたびに検査も直すことになり、割に合わない。

## テスト方針

正常系だけでなく、次を必ず検証する。

- 権限違反（ロール不足）
- 他 Workspace 参照
- 重複送信（冪等性）
- 競合（同時更新）
- 無効な状態遷移

テストの書き方の決めごとは [testing.md](testing.md) にある。

## 自動検証

- `main` へ入る前に、`pnpm verify` と同じ内容を GitHub Actions で通す。
  手元と CI で範囲を食い違わせないため、片方だけへ項目を足さない。
  実行するコマンドの一覧は [testing.md](testing.md) にある。
- 変更が届かない検証は走らせない。文書だけを変えたときにデータベースとブラウザを
  立ち上げても、合否は変わらないまま待ち時間だけが増える。
  どの変更で何が走るかは [testing.md](testing.md) にある。
- リポジトリの決めごと（`pnpm check:policy`）を足すときは、`scripts/check-policy.sh` の
  コメントへ「どの失敗を防ぐための検査か」を書く。一覧を文書へ書き写すと、
  検査を足すたびに二か所を直すことになる。
