# 検証

日常の変更は `pnpm check` で足ります。lint・型検査・単体テストを流し、DB は要りません。
残りは PR の CI が確かめます。手元ですべてを再現できる必要はありません。

| 検証 | コマンド | 要るもの |
| --- | --- | --- |
| 書式と静的検査 | `pnpm lint` | |
| 型検査 | `pnpm typecheck` | |
| 単体テスト | `pnpm test:unit` | |
| 統合テスト | `pnpm test:integration` | PostgreSQL |
| 画面テスト | `pnpm test:e2e` | PostgreSQL、ブラウザ |
| マイグレーションの適用漏れと内容の変更 | `pnpm db:verify` | PostgreSQL |
| リポジトリの不変条件 | `pnpm check:policy` | |
| 依存の既知脆弱性 | `pnpm check:audit` | 通信 |

`pnpm verify` は上をまとめて流し、既存 DB への移行と、書き出して戻したものの
突き合わせまで含めます。広い範囲を触ったときと、配る前に使います。
配れる状態かの判定は `pnpm verify:release-candidate` で、
コンテナのビルドと構成一覧まで含みます（[リリースの判定](../release/checklist.md)）。

## CI の分かれ方

| ワークフロー | 走る条件 | 中身 |
| --- | --- | --- |
| `ci.yml` | すべての PR と `main` への push | 何も立ち上げずに済む検証 |
| `runtime.yml` | 動かす対象が変わったとき | DB・ブラウザ・Docker を要する検証 |
| `windows-agent.yml` | 端末の配布物が変わったとき | Windows でしか確かめられない常駐の経路 |
| `audit.yml` | 依存が変わったときと、週に一度 | 依存の勧告 |
| `sbom.yml` | `main` への push と手動起動 | 配布物の構成一覧 |

分けているのは待ち時間を短くするためで、検証の範囲は減らしていません。
コードが変われば、関わるものがすべて走ります。

`runtime.yml` の対象は `paths` が決めます。push と pull_request で同じ一覧に
なっていることは `pnpm check:policy` が見ます。片方だけを直すと、PR で走った
検証が `main` で走らなくなります。

## 依存の脆弱性

`pnpm check:audit` は moderate 以上の勧告があれば失敗します。
すぐに直せないものは `scripts/audit-exceptions.txt` へ、勧告 ID・期限・理由を
書いて見送れます。期限を過ぎた見送りは、勧告が残っているかどうかに関わらず
失敗します。期限のない見送りを作らないためです。

## テスト用のデータベース

統合テストは `TEST_DATABASE_URL` のデータベースを使い、実行のたびにデータを消去します。
開発用データベースを誤って指さないよう、名前が `_test` で終わることを実行時に検査します。

ファイルは並列に流すため、実際に使うのは `TEST_DATABASE_URL` から作った
ワーカーごとのデータベース（`staffweave_test_w1` 〜 `w4`）です。
無ければ最初の実行で作り、そのあとは使い回します。消したい場合は手で落としてください。
同時に流す数は 4 で止めています。理由は `vitest.config.ts` にあります。

E2E はさらに別の `staffweave_e2e` を使い、専用のポート（API 8788 / Web 5174）でサーバーを起動します。
初回は `pnpm exec playwright install chromium` でブラウザを取得してください。

## テストの書き方

正常系だけでなく、権限違反・他ワークスペース参照・重複送信・同時更新・
無効な状態遷移も確かめます。

- テストが使う作り物（データベースの差し替え、送信の記録、資格情報の用意、
  検査用の一時データベース）は `packages/api/test/support/` へ置きます。
  ファイルごとに書き写すと、写し元によって振る舞いが変わります。
- `TEST_DATABASE_URL` の読み方は `test/database-url.ts` の 1 か所に限ります。
  経路によって開発データを消せる状態を残さないためです。
- 統合テストのアプリは `createTestApp` / `testAppFactory` から作ります。
  ファイルごとに組み立てると、現在時刻の渡し方や既定のワークスペースが変わります。
- 統合テストのデータは、既定ではテストごとに消します。
  読み取りだけを確かめる `describe` は `useSharedData` で準備を 1 度だけ作れます。
  書き換えるテストを混ぜると後のテストが前の結果を見るため、
  テストごとに表の行数を照合し、増減があればその場で落とします。

統合テストの所要が一部のファイルへ偏っていないことは、CI の `pnpm check:balance` が
見ます。秒数ではなくファイル間の比で見るのは、ランナーの速さが日によって変わるためです。
