# ロードマップ

どの順で作るかと、その順にする理由を書きます。

ここに書くのは順序と理由だけです。個々の課題の進み具合は GitHub の Issue と Pull Request、
機械的な合否は CI が正本です。同じ状態をこの文書へ写すと、必ずどちらかが古くなります。

いま何が動いていて何が無いかは [product/capability-matrix.md](product/capability-matrix.md) にあります。

## いまの位置

P15 までで、打刻・訂正・計算・申請・締め・端末・外部連携と、それらを支える監査、認可、
冪等性、DB 制約を作りました。後から直しにくいところを先に作った状態です。

P21 までで、勤務区分、法定の区分を持つ計算、労働形態、休暇の台帳、申請種別と段階承認も
API として動くようになりました。

画面は、打刻・当日の勤怠・承認待ち・異常・API キー・自分のセッションに加えて、
組織から申請種別までを設定する画面が動きます。

残っているのは、実機での確認と、利用者の身元まわり（招待・MFA・SSO）、
監視とバックアップの演習です。

## 順序の考え方

計算・制度・台帳の正本を先に作り、その上へ画面と連携を載せます。

先に画面や制度を作ると、単純な日次計算へ制度ごとの分岐を足し続けることになり、
あとで作り直すほかなくなります。休暇の画面を残数の台帳より先に作るのも同じ理由で避けます。

## P16 現状の能力と、作る順序を固める

これが無いと、リポジトリを受け取った側は製品の位置付けを判断できません。

## P17 時刻・訂正・業務日の完全性

完了しました。夏時間で業務日がずれない判定、打刻の再送とは別の訂正の範囲、
1 日に複数の勤務区間、拠点の時計での表示と入力を揃えました。

いちばん直しにくい「時刻の意味」をここで確定させています。

## P18 勤務区分と計算ルールの基盤

完了しました。版管理された勤務区分、固定休憩と自動休憩、みなし時間、シフト属性、
法定内外・法定休日と法定外休日・深夜の区分、遅刻早退、適用開始日つきの計算規則を揃えています。

労務計算の値は、法令上の普遍的な既定値として持ちません。事業者が設定します。
設定しないまま計算が進むと、誰も決めていない値が結果として残るためです。
未設定の区分は 0 ではなく「未設定」として示します。

## P19 労働形態

通常・フレックス・裁量・変形の割当を、期間つきで持てるようにしました。
制度ごとに必要な値がそろっていない割当は、DB の制約が断ります。

清算期間と対象期間の集計は P23 で作ります。日次の計算が正本になったので、
その上へ期間の集計を載せます。

## P20 休暇の台帳

付与・消化・失効・手当て・取消を追記で積む台帳を作りました。残数は保存せず、
任意の時点の値をその台帳から組み立てます。合計を保存すると、合計と記録が
食い違ったときに、どちらが正しいのかを決められません。

消化は期限の近い付与から先に減らします。残数を超える消化と、同じ記録の二度目の取消、
同じ申請からの二度目の消化は、DB の制約が断ります。

取得の単位と失効までの月数は事業者が設定します。設定しないかぎり、どちらも適用しません。

CSV での付与、自動付与、一斉付与は、管理画面と一括処理の土台ができる P22 で作ります。

## P21 申請区分と段階承認

申請種別を組織が定義し、1〜4 段の承認、差し戻し、出し直し、取消、代理を通せるようにしました。

承認の段数は、申請を出した時点の定義を写して申請へ持たせます。定義を都度参照すると、
承認の途中で段数を変えられたときに、承認した段が消えたり、承認していない段が現れたりします。

決裁の要求には、何段目・何回目の提出に対するものかを添えさせます。
古い画面から同じ承認を送り直しても、次の段へ進みません。

承認しきった休暇の申請は、その場で台帳へ反映します。途中の段では動かしません。

添付と通知は、外部への配送の形が決まる P24 と、画面ができる P22 で作ります。

## P22 管理画面

組織・拠点・部門・従業員・勤務区分・計算規則・労働形態・休暇種別・休暇台帳・
申請種別と承認経路を、画面から設定できるようにしました。

上でモジュールを切り替え、左でその中の設定を選びます。設定は数が多く、
一枚に並べると目的の項目まで辿り着けません。どこを見ているかは URL に持たせ、
読み込み直しても戻らず、人へ場所を伝えられるようにしています。

一覧・写して作る・CSV は 1 つの形にまとめました。CSV の列は画面の表と同じ定義から
作るため、列を足したときに片方だけが古くなりません。

見られない設定は節ごと出さず、入口も出しません。押せるボタンを出しておいて
403 を返すのでは、何ができるのかが利用者に伝わりません。

設定の一括取り込みは従業員の CSV だけです。他の設定を一括で入れる手段は、
帳票の形が固まる P23 のあとに判断します。

## P23 月次・レポート・給与連携

月次の集計、締める前の確認、再計算、締めた値の固定を作りました。

月次は日次から導きます。日次が正本で、月次だけを別に積み上げると合わなくなります。
1 日でも法定の閾値が未設定なら、その区分の月合計は出しません。0 にすると
「法定時間外が 0 分だった」と読めてしまい、計算していないことが伝わりません。

締めた時点の集計は、その場で固めます。締めたあとに打刻を訂正すると日次は
新しい版になりますが、給与へ渡した値は動きません。締めた値といまの値を並べ、
食い違っているときは印を付けます。給与連携の CSV も、締めた月は固めた値を出します。

再計算は、締めた月を動かしません。打刻も予定も過去の計算も無い日は、
やり直しても何も出ないため、計算そのものを作りません。

長時間労働の警告と休暇管理簿の帳票は、上限の設定をどこに持つかが決まってから作ります。
いまは月次の合計と休暇の台帳を CSV で取り出せます。

締めた月を出し直しても同じ結果になることを条件にします。

## P24 実機の打刻端末

**製品側の実装は揃いました。実機での確認は済んでいません。**

端末の常駐、送れなかった打刻のディスクへの保管、送る順番の維持、送れない間の間隔、
ログの秘匿、診断、Windows のサービスとして登録・削除する手順、配布物を作る手順を
作りました。IC カードの読み取り装置は取り決めだけを持ち、実装は含めません。

送信待ちは 1 件を 1 ファイルとして書きます。メモリだけに持つと、端末が落ちた時点で
消えます。消えた打刻は誰にも見えないため、あとから足すこともできません。

打刻は起きた順に送り、1 件でも送れなければそこで止めます。飛ばすとサーバー側の連番が
飛び、あとの打刻まで拒まれます。

実行ファイルは作りません。署名と配布の方式が決まっていない今、
署名なしの実行ファイルが出回ります。方式は P26 で決めます。

物理の IC カード、Windows のサービスとしての起動、再起動、回線の切断、時計のずれ、
端末の交換は、実機がある環境で確かめる必要があります。確かめる項目は
[operations/device-agent-service.md](operations/device-agent-service.md) の
チェックリストにあります。能力の一覧でも `partial` として示しています。

打刻時の位置情報は作っていません。同意と保持期間の扱いを決めてから作ります。

## P25 連携と運用の信頼性

Webhook の再試行、諦めた通知の置き場、手での送り直しを作りました。

送れなかったものは間を空けて送り直します。間隔は試行のたびに広げます。
広げないと、止まっている相手へ送り続けて復旧を妨げます。

相手が「その要求は受け取れない」と答えたものは送り直しません。
同じ要求を送り直しても、同じ答えしか返らないためです。

決めた回数を超えたら諦め、行は残したまま印を付けます。消すと、届かなかったこと自体が
分からなくなります。諦めた通知は一覧でき、人が中身を確かめてから手で送り直せます。

まだ無いもの:

- 招待、パスワード再設定、MFA、SSO、退職の処理
- メトリクスとアラート（構造化ログと相関 ID はあります）
- バックアップの暗号化と、復元の演習の自動化
- Row-Level Security の採否
- データの保持とアーカイブ

## P26 正式リリースの判定

判定を 2 段に分けました。混ぜると、片方だけが済んだ状態を
「リリースできる」と読んでしまいます。

**リリース候補**は、機械で確かめられる範囲がすべて通っていることです。
lint・型・単体・統合・画面（3 系統）・アクセシビリティ・移行（新規と既存の両方）・
書き出しと復元の突き合わせ・コンテナのビルド・構成一覧。すべて CI で走ります。

**正式リリース**は、そこへ実機・第三者・試行運用が加わります。
どれもこのリポジトリの検査では確かめられません。

手順と、人が確かめる項目の記録欄は
[release/checklist.md](release/checklist.md) にあります。

配るものと元にしたソースの対応は `pnpm release:manifest` で出します。
構成一覧には、元にした commit を書き込むようにしました。
書いていないと、受け取った側は載っている構成を作り直して確かめられません。

タグと署名はこの手順に含めません。署名には所有者の鍵が要り、
鍵を持たない者が付けた署名は「誰が配ったか」を示せません。

ここで初めて、正式リリースのチェックリストを作ります。

- まっさらな環境での標準の検証、マイグレーション、ブラウザ、アクセシビリティ、
  視覚回帰、計算のゴールデンテスト、負荷と障害、復元の演習、外部のレビュー、
  実運用での試行を通す
- 成果物、タグ、署名、SBOM の対応を決める

通したことを示す記録の形式も、このときに決めます。
実際の CI と配布の方式が分かってからでないと、形だけが先に固まります。
