# ロードマップ

各フェーズは独立したブランチと PR で進めます。

この文書が持つのは、フェーズの順序、公開条件、Issue 群の分類だけです。
個々の Issue の状態、検証結果、コミットの対応表はここへ写しません。
同じ完了状態を複数の場所へ記録すると、必ずどこかが古くなり、
どれが正しいのかを確かめる作業が増えるためです。

## 情報の正本

| 情報 | 正本 |
| --- | --- |
| 要求、再現条件、完了条件、優先度 | GitHub Issue |
| 実装差分、設計判断、検証結果 | Pull Request |
| 機械的な合否 | CI |
| 長期的な原則、構造、運用方法 | `docs/` |
| 大まかな実施順と公開条件 | この文書 |
| 実装済みの DB 構造 | SQL マイグレーション |
| API 契約 | OpenAPI |
| 現在のコード依存関係 | `package.json` と実装 |

次のものは正本にしません。

- Issue と同じ状態を複製したタスクファイル
- PR と同じ検証結果を保存する進捗ファイル
- コミット SHA を手作業で同期する計画ファイル
- 実装と独立して更新が必要な状態管理メタデータ

公開できる水準であること、システム全体として安全であることは含みません。
過去のフェーズ番号、コミット、Issue、PR は遡って変更しません。

**公開判定: 保留。**
P14 で実装したのは外部連携の初期実装までです。
実装後のレビューで見つかった認可の適用漏れ・競合制御・秘密情報の扱いは、
P15 の各単位で解消し、登録していた GitHub Issue はすべて閉じました。

残っているのはライセンス方針の決定です。これは実装ではなく事業判断であり、
Agent による自動変更は行いません。決まるまで公開も実データの投入も行いません。

CI は P14 をマージした後に導入しました。
検証の内容と実行するコマンドは [development-policy.md](development-policy.md) を参照してください。

## 各フェーズの範囲

### P0 基盤初期化

README、ライセンス、開発方針、日英用語集、モジュール境界、ロードマップ。

### P1 セルフホスト基盤

pnpm workspace、TypeScript 設定、Hono サーバー、React/Vite クライアント、
PostgreSQL、SQL マイグレーション、Docker Compose、health / readiness、ローカル起動手順。

### P2 組織と認証

Workspace、組織、拠点、部門、利用者、従業員、ロール、ローカル認証、セッション、
テナント境界の強制、日本語・英語切り替え。

### P3 最小打刻

一人・一日を対象とした出勤・退勤、当日表示、不変の打刻イベント、
冪等な二重送信防止、監査記録。

### P4 休憩と修正

休憩開始・終了、複数休憩、日跨ぎ勤務、打刻修正、修正理由、変更前後の記録、履歴表示。

### P5 勤務予定と計算

勤務カレンダー、勤務パターン、所定労働時間、実労働、休憩、所定内外、休日、深夜帯を扱う
決定的な計算エンジン。入力版・ルール版・計算根拠の保存。

### P6 申請・承認・締め

日次申請、承認、差し戻し、取消、コメント、月次締め、締め解除、確定後の編集制御。
状態遷移は fsmxjs を使う。

### P7 スマートフォン打刻

モバイル優先の打刻 UI、明確な状態表示、ワンタップ操作、オフライン待機、再送、
冪等受理、アクセシビリティ。

### P8 打刻端末プロトコル

端末登録、端末資格情報、署名イベント、連番、再送、失効、Agent シミュレーター、
JSON Schema、OpenAPI。OS 固有実装は行わない。

### P9 IC カード試作

ローカル Agent 用のカード資格情報アダプター。生のカード識別子を直接保存せず、
登録・失効・重複防止・出退勤を扱う。実機非依存のテスト用アダプターを用意する。

### P10 PC セッション試作

ログイン・ログオフ・ロック・解除の観測イベントを扱う Agent 境界とシミュレーター。
勤怠との乖離を本人・管理者へ提示する。自動確定はしない。

### P11 柔軟な勤務制度

休暇、欠勤、休日、変則的な勤務周期、週休 3 日、複数勤務パターン、有効期間付き設定。
曜日固定や週 5 日勤務をコアへ埋め込まない。

### P12 複数組織と契約

雇用元、勤務先、受入組織、契約期間、配属、勤務先別の閲覧権限、外部承認者、
日次・月次承認。

### P13 監査と異常検出

打刻と PC 記録の乖離、確定後変更、大量修正、端末時計差、連番欠落、重複イベントの検出。
根拠付きで表示・出力できるようにする。

### P14 外部連携の初期実装

CSV 入出力、汎用給与出力、Webhook、API キーとスコープ、connector SDK、
バックアップ・復元、サンプルデータ、デモモード、セルフホスト導入手順。

ここで実装したのは各機能の最初の形までです。公開に必要な水準に達しているかは
P15 で判定します。P12 も同様に、契約・配属・閲覧範囲の登録までを範囲としており、
関連機能を網羅した状態ではありません。

### P15 公開前の品質ゲート

P15 は新機能のフェーズではありません。公開判定を行うための品質ゲートです。
新しい機能を足す前に、公開を妨げるセキュリティ・整合性・認可・運用上の問題を解消します。

作業単位は下のとおり分類します。ここに書くのは分類と実施順だけで、
各 Issue の内容・再現条件・完了条件は Issue 側を正本とします。

| 単位 | 範囲 | Issue |
| --- | --- | --- |
| R0 | 開発管理の正本を Issue・PR・CI・恒久文書へ一本化する | （この文書の改訂） |
| R2 | Webhook の送信境界 | #25, #18, #26 |
| R3 | 端末・打刻イベントの整合性 | #19, #20, #21, #24 |
| R4 | 秘密情報と Workspace 分離 | #22 |
| R5 | 組織・契約・適用期間の DB 整合性 | #23, #29 |
| R6 | 認可と参照日の統一 | #37, #35 |
| R7 | API・時刻・依存境界 | #27, #30, #34 |
| R8 | 検証・移行・コンテナ運用 | #28, #31, #32, #33 |

R2 から R8 までの Issue はすべて解消しました。実施した内容は各 PR を正本とします。

R2 は #25（トランザクション境界）、#18（送信先の防御）、#26（署名鍵モデル）の順に、
それぞれ別の PR で行います。守る対象が違うため、まとめるとレビューの範囲が広くなりすぎます。

P15-R2B が守るのは、Webhook 送信先を使った内部ネットワークへの到達です。
送信先の登録時と送信の直前の両方で名前解決の結果を検査し、検査したアドレスへ接続を固定します。
名前解決の上限時間と、複数の接続候補の扱いもここに含みます。
送信の到達保証（再送・デッドレター）は範囲外で、P20 で扱います。

P15-R2C が正すのは、保存している署名鍵の名称と説明が実際の役割と食い違っていることです。
対称鍵の HMAC-SHA256 と既存送信先との署名互換性は変えず、保存値が署名を生成できる機密情報で
あることをコード・DB・文書で一致させます。署名方式の変更、非対称署名、鍵のローテーション API、
署名鍵のアプリケーションレベル暗号化は範囲外です。

R3 は原則として 1 Issue につき 1 PR とし、#20 と #21 には DB 制約と並行実行テストを必須とします。
実施順は次のとおりです。進行状態と完了状態は、各 Issue および PR を正本とします。

| 単位 | 範囲 | Issue |
| --- | --- | --- |
| P15-R3A | 端末・カード登録トークンの原子的な消費 | #20 |
| P15-R3B | PC セッション観測の連番と冪等性 | #21 |
| P15-R3C | モバイルの送信待ちにおける利用者の分離 | #19 |
| P15-R3D | カード打刻の再送に対する応答の再現 | #24 |

登録トークンは、端末とカードを打刻の入力元として認めるための資格です。
入力元を名乗る側の資格を先に確定させ、そのうえで届いたイベントの整合性へ進みます。

P15-R3B が正すのは、PC セッション観測が連番を検査せず、同時再送を重複保存できることです。
端末ごとの連番は経路ごとに分けず、打刻イベント・カード打刻・PC セッション観測で共有します。
同じ要求を二度受け取らないことは、要求単位の受領記録と DB の一意制約で決めます。
1 回の要求には観測が複数入るため、観測そのものへ冪等キーの一意制約は置きません。
観測から勤務時間を自動確定させることは、ここでも行いません。

R5 はアプリケーション側の検査だけでなく、複合外部キー・一意制約・排他制約を使います。
R6 は着手前に API 種別ごとの参照日を表で固定し、SQL 実装とインメモリ実装で同じ方針を共有します。

認可については、閲覧範囲の適用漏れ（#17）を是正したうえで、
契約と配属の期間を認可で見ていない問題（#37）が残っています。

ライセンスは現在 MIT です。当初 AGPL-3.0 を想定していた経緯があるため、
次を確認したうえで方針を決めます。これは事業判断であり、Agent による自動変更は行いません。
P15 で残っているのはこの判断だけです。

- Git 履歴上の著作者とコントリビューター
- 外部コードの取り込みの有無
- 依存ライセンス
- セルフホスト版の再配布方針
- 改変した SaaS にソース公開を求めるか
- SDK を別ライセンスにするか

## 公開判定チェックリスト

次をすべて満たすまで、公開可能とは判定しません。

| 条件 | 状態 |
| --- | --- |
| `release-blocker` の Issue が 0 件 | 満たす |
| 重大度の高い Issue に、対応するか見送るかの明示的な判断がある | 満たす（すべて対応） |
| `main` の CI が成功している | 満たす |
| ローカルの完全検証（`pnpm verify`）が成功している | 満たす |
| 空のデータベースへの全マイグレーションが成功する | 満たす |
| 既存データベースへの連続マイグレーションが成功する | 満たす |
| バックアップと復元の検証が成功している | 満たす |
| コンテナが非 root かつ production build で起動する | 満たす |
| Workspace 境界の負のテストが成功している | 満たす |
| 認可の適用期間テストが成功している | 満たす |
| OpenAPI と実際の経路が一致している | 満たす |
| README が未提供の機能を提供済みと表現していない | 満たす |
| セルフホスト運用のセキュリティ前提が明記されている | 満たす |
| ライセンス方針が確定している | **未** |
| Git 履歴に秘密情報が含まれていないことを確認済み | 満たす |

一つでも欠けている間は、公開も実データの投入も行いません。
状態の根拠は各 PR と CI にあります。この表は現時点の要約であり、
個々の検証結果をここへ写しません。
