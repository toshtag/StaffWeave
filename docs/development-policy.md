# 開発方針

staffweave の実装判断で迷ったとき、この文書が優先されます。

## 名称

- 正式名称は常に `staffweave`。`staff-weave` や `StaffWeave` へ変形しない。
- npm パッケージのスコープは `@staffweave/*`。
- 外部製品の固有名詞を、コード・コメント・文書・ファイル名・テスト・コミット・PR へ残さない。

## 言語

- 仕様・文書・コメント・コミット・PR の基本言語は日本語。
- UI は `ja-JP` と `en` に対応する。
- 識別子・API・DB 名は自然な英語を使う。機械的な直訳は避ける。
  対応表は [glossary.md](glossary.md)。

## 技術選定

| 領域 | 採用 |
| --- | --- |
| 言語 | TypeScript（strict） |
| 実行環境 | Node.js LTS |
| パッケージ管理 | pnpm workspace |
| データベース | PostgreSQL |
| HTTP | Hono |
| フロントエンド | React + Vite |
| テスト | Vitest（unit / integration）、Playwright（E2E） |
| 実行構成 | Docker Compose |
| 同期状態遷移 | fsmxjs |

導入しないもの: マイクロサービス、Kubernetes、Redis、Kafka、ORM による暗黙のクエリ生成。

## アーキテクチャ制約

- モジュラーモノリスから開始する。
- ドメイン、勤怠計算、状態遷移、API 契約をフレームワークから分離する。
- React 型、Hono 型、DB 型、外部 SDK 型をドメイン層へ持ち込まない。
  ドメイン層が依存してよいのは TypeScript 標準ライブラリと fsmxjs のみ。
- DB アクセスは明示的な SQL と Repository 境界を基本とする。
- OpenAPI 3.1 と JSON Schema を Web・Agent・外部連携の共通契約にする。
- fsmxjs は申請・承認・締め・端末登録などの同期状態遷移に限定して使う。
  非同期処理やデータ取得の制御には使わない。

## データの扱い

- 元の打刻・観測イベントは上書きしない。修正・承認・計算版を追跡可能にする。
- PC ログや IC カード情報だけで勤務時間を自動確定しない。証拠・候補・乖離検出として扱う。
- 生のカード識別子など、再利用されると危険な値はそのまま保存しない。
- 秘密情報、実在人物、実在企業のデータをコミットしない。

## テナント境界

- すべての業務データは `workspace_id` を持つ。
- Repository は `workspace_id` を必須引数として受け取り、SQL の `WHERE` 句に必ず含める。
- 他 Workspace のデータを参照できないことをテストで検証する。

## 表現の制約

- 完全な不正防止や法令適合を保証する表現をしない。
- 未実装機能を README や UI で提供済みと表現しない。

## 実装の進め方

- 各フェーズの受け入れ条件を先に短く定義してから実装する。
- 文書を先に大量作成せず、実装に必要な最小限を同じフェーズで更新する。
- 使われない抽象化、空パッケージ、将来用だけのコードを作らない。
- 一時的な TODO を残す場合は、理由と解消条件を明記する。
- フェーズ外の問題は勝手に拡張せず、重大でなければ記録して次へ進む。
- 課題と完了条件は GitHub Issue、実装差分と検証結果は PR を正本とし、
  同じ状態を写した進捗ファイルをリポジトリへ増やさない。
  実施順と公開条件は [roadmap.md](roadmap.md) を参照する。

## テスト方針

正常系だけでなく、次を必ず検証する。

- 権限違反（ロール不足）
- 他 Workspace 参照
- 重複送信（冪等性）
- 競合（同時更新）
- 無効な状態遷移

## Git 運用

- フェーズごとに作業ブランチ（`p15/webhook-outbox` のようにフェーズ番号を接頭辞にする）を作る。
- 意味のある小さなコミットを複数作る。コミット前に対象テストと静的検証を実行する。
- PR は日本語で作成し、検証成功後に merge commit 方式で `main` へマージする（squash しない）。
- 履歴の改変、`main` への force push、検証失敗状態でのマージを禁止する。
- コミットと PR に、生成ツールに由来する定型文・署名・リンクを含めない。

## 自動検証

`main` へ入る前に、次をすべて機械的に通します（GitHub Actions）。
コンテナのビルド以外は `pnpm verify` が同じ内容をまとめて実行します。
手元と CI で検証の範囲を食い違わせないため、片方だけへ項目を足しません。

| 検証 | コマンド |
| --- | --- |
| 依存の再現性 | `pnpm install --frozen-lockfile` |
| lint と format | `pnpm lint` |
| 型検査 | `pnpm typecheck` |
| 単体テスト | `pnpm test:unit` |
| 統合テスト | `pnpm test:integration` |
| 画面テスト | `pnpm test:e2e` |
| マイグレーション | `pnpm db:migrate`（二度実行）、`pnpm db:verify` |
| リポジトリの決めごと | `pnpm check:policy` |
| コンテナのビルド | `docker build -f docker/api.Dockerfile` |

`pnpm check:policy` が見るのは、レビューで見落としやすく、後から直すと影響が大きいものだけです。

- 正式名称が `staffweave` から変形していないか
- `.env`、端末の資格情報、秘密鍵、API キーがコミットされていないか
- 生成ツールに由来する定型文が含まれていないか
- マイグレーションの版番号とファイル名が規約どおりか
- ドメイン層がフレームワークや上位パッケージへ依存していないか
- パッケージの依存方向が [module-boundaries.md](module-boundaries.md) のとおりか
