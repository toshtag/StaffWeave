# 開発方針

StaffWeave の実装判断で迷ったとき、この文書が優先されます。

## 設計の前提

以下は個別の判断より上位にあり、下の各節はこの前提を具体化したものです。

- **セルフホスト優先。** 単一の PostgreSQL と Docker Compose で起動できることを最優先にする。
  同一コードベースで将来 SaaS 運用できるよう、Workspace 分離は最初から持つ。
- **モジュラーモノリス。** マイクロサービス、Kubernetes、Redis、Kafka は導入しない。
- **観測イベントは不変。** 打刻の取り消しや修正は、元イベントを書き換えず追加記録で表現する。
- **自動確定しない。** PC ログや IC カードの記録だけで勤務時間を確定させない。
  これらは証拠・候補・乖離検出として扱う。

## 名称

- 読ませる名前は常に `StaffWeave`。文書の本文、画面の表示、コードの説明文はこの形で書く。
- 機械が読む名前は小文字の `staffweave`。npm パッケージのスコープ（`@staffweave/*`）、
  compose が作るものの名前、HTTP ヘッダー、データベース名と接続情報がこれにあたる。
  すでに動いているものの名前を、読ませる名前に合わせて変えない。
- `staff-weave` の形は、どちらの用途でも使わない。
- 外部製品の固有名詞を、コード・コメント・文書・ファイル名・テスト・コミット・PR へ残さない。

## 言語

- 仕様・文書・コメント・コミット・PR の基本言語は日本語。
- UI は `ja-JP` と `en` に対応する。
- 識別子・API・DB 名は自然な英語を使う。機械的な直訳は避ける。
  対応表は [glossary.md](glossary.md)。

## 技術選定

| 領域 | 採用 |
| --- | --- |
| 言語 | TypeScript（strict） |
| 実行環境 | Node.js LTS |
| パッケージ管理 | pnpm workspace |
| データベース | PostgreSQL |
| HTTP | Hono |
| フロントエンド | React + Vite |
| テスト | Vitest（unit / integration）、Playwright（E2E） |
| 実行構成 | Docker Compose |
| 同期状態遷移 | fsmxjs |

導入しないもの: マイクロサービス、Kubernetes、Redis、Kafka、ORM による暗黙のクエリ生成。

## アーキテクチャ制約

- モジュラーモノリスから開始する。
- ドメイン、勤怠計算、状態遷移、API 契約をフレームワークから分離する。
- React 型、Hono 型、DB 型、外部 SDK 型をドメイン層へ持ち込まない。
  ドメイン層が依存してよいのは TypeScript 標準ライブラリと fsmxjs のみ。
- DB アクセスは明示的な SQL と Repository 境界を基本とする。
- OpenAPI 3.1 と JSON Schema を Web・Agent・外部連携の共通契約にする。
- 外から来る値（本文・経路の識別子・クエリ文字列）は、契約で検証してから先へ渡す。
  検証は経路ごとに書かず、共通の入口（`packages/api/src/shared/request.ts`）を通す。
  経路ごとに書くと、書いた経路だけが契約どおりになる。
- 経路が受け取る引数は、契約に宣言したものと一致させる。
  契約にあって読まない引数、読んでいて契約に無い引数を残さない。
- fsmxjs は申請・承認・締め・端末登録などの同期状態遷移に限定して使う。
  非同期処理やデータ取得の制御には使わない。

## データの扱い

- 元の打刻・観測イベントは上書きしない。修正・承認・計算版を追跡可能にする。
- PC ログや IC カード情報だけで勤務時間を自動確定しない。証拠・候補・乖離検出として扱う。
- 生のカード識別子など、再利用されると危険な値はそのまま保存しない。
- 秘密情報、実在人物、実在企業のデータをコミットしない。

## テナント境界

- すべての業務データは `workspace_id` を持つ。
- Repository は `workspace_id` を必須引数として受け取り、SQL の `WHERE` 句に必ず含める。
- 他 Workspace のデータを参照できないことをテストで検証する。

## 表現の制約

- 完全な不正防止や法令適合を保証する表現をしない。
- 未実装機能を文書や UI で提供済みと表現しない。
  動作するものの一覧は [features.md](features.md) を正本とし、README へ写さない。

## 実装の進め方

- 各フェーズの受け入れ条件を先に短く定義してから実装する。
- 文書を先に大量作成せず、実装に必要な最小限を同じフェーズで更新する。
- 使われない抽象化、空パッケージ、将来用だけのコードを作らない。
- 一時的な TODO を残す場合は、理由と解消条件を明記する。
- フェーズ外の問題は勝手に拡張せず、重大でなければ記録して次へ進む。
- 課題と完了条件は GitHub Issue、実装差分と検証結果は PR を正本とし、
  同じ状態を写した進捗ファイルをリポジトリへ増やさない。
  実施順と公開条件は [roadmap.md](roadmap.md) を参照する。

## テスト方針

正常系だけでなく、次を必ず検証する。

- 権限違反（ロール不足）
- 他 Workspace 参照
- 重複送信（冪等性）
- 競合（同時更新）
- 無効な状態遷移

テストが使う作り物（データベースの差し替え、送信の記録、資格情報の用意、
検査用の一時データベース）は `packages/api/test/support/` へ置き、
実行用のコードへは入れません。ファイルごとに書き写すと、写し元によって振る舞いが変わり、
写し間違えたテストが通ってしまいます。

`TEST_DATABASE_URL` の読み方は `test/database-url.ts` の 1 か所に限ります。
検査ごとに読み方を変えると、経路によって開発データを消せる状態が残ります。

統合テストのアプリは `createTestApp` / `testAppFactory` から作ります。
ファイルごとに `createApp` を組み立てると、現在時刻の渡し方や既定のワークスペースが
写し元によって変わり、写し間違えたテストが時刻を進められなくなります。

## Git 運用

- フェーズごとに作業ブランチ（`p15/webhook-outbox` のようにフェーズ番号を接頭辞にする）を作る。
- 意味のある小さなコミットを複数作る。コミット前に対象テストと静的検証を実行する。
- PR は日本語で作成し、検証成功後に merge commit 方式で `main` へマージする（squash しない）。
- 履歴の改変、`main` への force push、検証失敗状態でのマージを禁止する。
- コミットと PR に、生成ツールに由来する定型文・署名・リンクを含めない。

## 自動検証

`main` へ入る前に、次をすべて機械的に通します（GitHub Actions）。
コンテナのビルド以外は `pnpm verify` が同じ内容をまとめて実行します。
手元と CI で検証の範囲を食い違わせないため、片方だけへ項目を足しません。

| 検証 | コマンド |
| --- | --- |
| 依存の再現性 | `pnpm install --frozen-lockfile` |
| lint と format | `pnpm lint` |
| 型検査 | `pnpm typecheck` |
| 単体テスト | `pnpm test:unit` |
| 統合テスト | `pnpm test:integration` |
| 画面テスト | `pnpm test:e2e` |
| マイグレーション | `pnpm db:migrate`（二度実行）、`pnpm db:verify` |
| リポジトリの決めごと | `pnpm check:policy` |
| 依存の脆弱性 | `pnpm check:audit` |
| コンテナのビルドと起動 | `docker build -f docker/api.Dockerfile`、通信を切って入口が動くかの確認 |
| 配布物の構成一覧 | `pnpm sbom:generate`、`pnpm sbom:verify`（専用ジョブ） |

`pnpm check:policy` が見るのは、レビューで見落としやすく、後から直すと影響が大きいものだけです。

- 名称に `staff-weave` の形が使われていないか
- 文書の本文の名前が `StaffWeave` になっているか
- `.env`、端末の資格情報、秘密鍵、API キーがコミットされていないか
- 生成ツールに由来する定型文が含まれていないか
- ライセンスの表示が `LICENSE`・README・決定の記録で一致しているか
- `LICENSE` の著作権表示が権利者の名義になっているか
- 正式リリース判定の記録が残っているか
- SBOM の生成・検証の手順と文書が揃っているか
- SBOM の生成物を追跡していないか
- SBOM のジョブが使う Action をコミット SHA で固定しているか
- 依存の版指定がパッケージ間で揃っているか（`@types/node`・`tsx`・`typescript`・`vitest`）
- `@types/node` の major と、コンテナの Node の major が `.nvmrc` と一致しているか
- PostgreSQL の版が `docker-compose.yml` と CI で揃い、tag が major と基盤を含む形か
- 照合順序の指定が `docker-compose.yml` と CI で揃い、プロバイダが builtin か
- PostgreSQL のデータの置き場が、その版の配置に合っているか
- `docker compose` が作るもの（プロジェクト・ネットワーク・ボリューム）の名前を決めているか
- コンテナの入口が pnpm を介していないか
- コンテナのビルドの定義が 1 つにまとまっているか
- `.dockerignore` が、ビルドへ渡すものを明示する形になっているか
- 文書どうしのリンクがすべて辿れるか
- `docs/README.md` の索引に、すべての文書が載っているか
- 旧い認可契約（閲覧範囲が空なら全件）の説明が残っていないか
- マイグレーションの版番号とファイル名が規約どおりか
- ドメイン層がフレームワークや上位パッケージへ依存していないか
- パッケージの依存方向が [module-boundaries.md](module-boundaries.md) のとおりか

名称の検査が本文として見るのは `*.md` だけです。設定と実行用のコードには、接続情報や
コンテナの名前として小文字がそのまま並ぶため、同じ規則では読ませる名前と区別できません。
本文へ書いた名前は前後に繋がりを持たず、機械が読む名前は必ず何かと繋がった形で現れます
（`@staffweave/*`、`staffweave-db`、`x-staffweave-`、コード表記の前後の記号）。
この違いだけを手掛かりにします。

認可契約の検査は、例外として認めた 2 ファイルの検出件数まで固定します。
例外の範囲が知らないうちに広がると、検査が通っていても旧い説明が増えていきます。

ライセンスと正式リリース判定の検査は、文書に書いてある事実だけを見ます。
GitHub の Issue や PR の件数は取りに行きません。ネットワークを必要にすると
オフラインで検証できなくなり、GitHub の障害でコードの検証まで失敗します。
Issue の現在の状態は GitHub を正本とし、正式リリースのたびに数え直します
（[release-readiness/](release-readiness/)）。

SBOM の生成と検証は `pnpm verify` に含めません。Docker と外部の道具が要るため、
通常の開発でオフライン検証ができなくなり、変更の確認も遅くなります。
専用の CI ジョブと、正式リリース前の確認で実行します
（[security/sbom.md](security/sbom.md)）。

コンテナの検査が守るのは、動かしている間に増えていくものです。名前を決めずに置くと
compose が置き場所から作るため、同じものを別の場所へ置いただけで一覧が増えます。
実行段へ pnpm を置くと、動かすのに要らない容量を配ったうえ、置き場を消した形では
コンテナを起動するたびに取り寄せに行き、通信できない環境では起動できません。
入口が pnpm を介していないことは CI が実際に通信を切って確かめます
（[deployment.md](deployment.md)）。

依存の版の検査が守るのは、宣言と実行環境の食い違いです。実行環境の major は `.nvmrc` を
正本とし、型定義（`@types/node`）をそこより先へ進めません。先へ進めると、実行環境に無い
API が型検査だけ通り、実行時に落ちます。データベースは `docker-compose.yml` と CI が
同じ major であることを見ます。片方だけを上げると、手元で通った SQL が別の版で走ります。

照合順序の検査が守るのは、並びが OS へ引きずられることです。プロバイダを builtin へ
固定し、compose と CI で同じ指定を使います。libc の照合順序は版で変わることがあり、
変わると `text` の索引が黙って狂います（[decisions/0003-database-collation.md](decisions/0003-database-collation.md)）。

`pnpm check:audit` は、依存に moderate 以上の既知脆弱性があれば失敗させます。
すぐに直せないものは `scripts/audit-exceptions.txt` へ、勧告 ID・期限・理由を書いて見送れます。
期限を過ぎた見送りは、勧告が残っているかどうかに関わらず失敗します。
期限のない見送りを作らないためです。
